# Project 1 — Data Governance Program

Stands up a working data-governance program over a synthetic fintech data estate, on **BigQuery + OpenMetadata**: a catalog with **column classification**, a **business glossary**, **data-ownership**, and **data-quality** monitoring — with classification gaps and quality issues deliberately seeded in, so the governance work is real rather than cosmetic.

This project is the foundation the rest of the portfolio builds on: it produces the data estate that [Project 3 (automation)](../03-grc-automation/) monitors and [Project 4 (AI in GRC)](../04-ai-in-grc/) classifies, and it operates the classification and access-review controls (**DP-01**, **AC-02**) tested in [Project 2 (audit)](../02-soc2-iso-audit/).

> Everything here is **fictional/synthetic**. The estate is randomly generated; no real data.

## What it demonstrates

- Designing a **data classification standard** and applying it at column level.
- A **hub-and-spoke ownership model** (owners, stewards, custodians).
- Building a **business glossary** and linking terms to data.
- Defining and running **data-quality rules** across six dimensions, with a remediation log.
- Doing all of the above in a real open-source **data catalog** (OpenMetadata) over **BigQuery** — demonstrable catalog-tool experience.

## The data estate

Eight tables of synthetic fintech data (generated by [`scripts/generate_estate.py`](scripts/generate_estate.py)):

| Table | Rows | Notable sensitive columns |
|---|---|---|
| `customers` | 500 | ssn, email, phone, date_of_birth, address |
| `bank_clients` | 8 | routing_number, api_key_hash |
| `accounts` | 800 | balance |
| `cards` | 600 | card_number, card_expiry, cardholder_name |
| `transactions` | 4000 | amount |
| `lending_applications` | 700 | annual_income, credit_score |
| `console_users` | 120 | email (workforce) |
| `audit_log` | 2000 | — |

**Seeded on purpose** (so there's something to find): classification "traps" (e.g., `api_key_hash`, `card_expiry`, `console_users.email` are commonly under-classified) and data-quality defects (null/invalid/duplicate emails, orphaned accounts, out-of-range credit scores, inconsistent status casing).

## Walkthrough

### Prerequisites
- Python 3 (standard library only — no packages needed)
- A Google account and a **BigQuery sandbox** project (free, no credit card): https://console.cloud.google.com/bigquery
- `gcloud` + `bq` CLI, authenticated (`gcloud auth login`)
- **Docker** 20.10+ and **Docker Compose** v2, with ≥ 6 GiB RAM allocated

### Step 1 — Generate the estate
```bash
cd scripts
python3 generate_estate.py        # writes CSVs to ../data/
python3 run_data_quality.py       # writes ../data/remediation_log.csv
```

### Step 2 — Load into BigQuery
```bash
./load_to_bigquery.sh YOUR_PROJECT_ID northlake US
```
This creates a `northlake` dataset and loads the eight tables (schema auto-detected).

### Step 3 — Stand up OpenMetadata
```bash
mkdir openmetadata-docker && cd openmetadata-docker
curl -sL -o docker-compose.yml \
  https://github.com/open-metadata/OpenMetadata/releases/download/2.1.0-release/docker-compose.yml
docker compose -f docker-compose.yml up --detach
```
Open **http://localhost:8585** — log in with `admin@open-metadata.org` / `admin`.
*(Check the OpenMetadata releases page for the current version if 2.1.0 has moved.)*

### Step 4 — Connect OpenMetadata to BigQuery
1. In GCP, create a **service account** with roles **BigQuery Data Viewer** and **BigQuery Metadata Viewer** (read-only is enough), and download its **JSON key**. *Keep this key out of the repo — it's gitignored.*
2. In OpenMetadata: **Settings → Services → Databases → Add New Service → BigQuery**. Paste the service-account JSON and your project ID.
3. Add a **Metadata** ingestion and run it — the eight tables appear in the catalog.
4. Optionally enable the **Profiler** ingestion to populate column statistics.

### Step 5 — Classify, define, and own
- **Classification tags:** create a `DataClassification` tag category with `Restricted / Confidential / Internal / Public`. Apply them to columns using [`column-classification-map.csv`](governance/column-classification-map.csv) as the key. Try OpenMetadata's **auto-classification/PII** first, then check it against the map — note what it missed (the "commonly missed" columns are the interesting ones).
- **Glossary:** **Govern → Glossary → Import** and upload [`business-glossary.csv`](governance/business-glossary.csv). Link terms (e.g., *Cardholder Data*) to the relevant columns.
- **Ownership:** assign each table an **Owner** and domain per [`data-ownership-model.md`](governance/data-ownership-model.md).

### Step 6 — Data quality in the catalog
Recreate the [DQ rules](governance/data-quality-rules.md) as **Table/Column Tests** in OpenMetadata (e.g., column-values-to-be-between for `credit_score` 300–850; not-null for `email`). Run them; the catalog shows a live pass/fail status per table. The committed [`remediation_log.csv`](data/) is the same checks run locally.

### Step 7 — Capture it for the portfolio
Screenshot the running catalog into [`screenshots/`](screenshots/): the classified `customers` table, the glossary, a failing DQ test, and an owned domain. A reviewer who sees those knows you *operated* a catalog, not just described one.
